## 1. 决策摘要

现有证据支持的路线是：**维持官方固件、内核、uClibc 和系统共享库；只在 `/userdisk/data` 上构建和安装可回滚的私有用户态程序。** `/userdisk/data` 是独立硬盘分区；根文件系统只剩约 20 MB，不能把新依赖装入根分区。

| 次序 | 组件 | 当前证据 | 决策 | 优先理由 |
|---|---|---|---|---|
| A0 | Samba 服务与 1.0.7 兼容层 | Samba 4.25.1 运行；1.0.7-r2d 已装机，访客 ACL 有规则面和 cron 自愈证据 | **先完成现有版本验收**；确认当前 nmbd 身份、整机重启；访客端到端保持 BLOCKED 直到有可用 BSS/访客客户端 | 这是已部署主服务的收尾，不是再做一次同版本升级 |
| A1 | Samba 上游维护 | 上游当前 stable 为 4.25.1；设备运行同版；项目有适配 GCC 4.8.2/uClibc 的补丁和回归链 | **暂不重复升级**；遇到后续上游版本/安全修复时，单独开版本迁移 | 避免为版本号变更承担无收益的生产切换 |
| B1 | Dropbear SSH 服务端 | 2011.54，TCP 22 对 LAN/访客网可达 | **优先构建候选版**；先并行测试，再决定是否接管 22 | 旧版本和旧算法是当前最清楚的可达老服务风险 |
| B2 | curl | 7.33.0，PolarSSL 1.3.16；是客户端 | **做独立构建评估**；仅在确认调用方且 TLS 测试通过后部署 | 旧客户端有更新收益，但当前调用方和实际使用协议尚未盘清 |
| B3 | `nmbd` | 原厂 4.0.21 的历史现场快照运行于 UDP 137/138；4.25.1 产物已随 Samba 构建 | **重新确认现状后再切换**；复用 4.25.1 私有树，不单独替换 `samba_multicall` | 已有可用候选产物，但仍属 SMB/NetBIOS 链路 |
| B4 | MiniDLNA / ReadyMedia | 1.1.0；一次设备清点时未运行，但配置启用且管理链可拉起 | **保留为条件候选**；先确认用户是否使用 DLNA，再做替代包测试 | 会触及小米配置生成、TaskMonitor/supervisord 和媒体索引行为 |
| B5 | dnsmasq | 2.71；设备清点时未运行，本机没有 53 端口监听 | **暂缓**；除非明确把本机作为 DNS/DHCP 服务端 | 当前没有服务收益，启用会改变网络核心行为 |
| B6 | WebDAV 文件共享（新功能候选） | 当前固件没有已确认的 WebDAV 服务；现有全盘访问策略以 `/etc/config/macfilter` 的设备 `lan` 字段表达，1.0.7 兼容层只对 SMB 端口执行 | **可行，建议作为 SMB 的可选补充**；优先评估隔离部署的 lighttpd `mod_webdav`，复用同一设备授权策略；先隔离验证，再决定是否设备部署 | HTTP/WebDAV 便于无 SMB 客户端时访问；但需新监听端口、认证/TLS、文件权限和访客隔离，不能直接借用小米管理 Web 服务 |
| — | OpenSSL 系统库、BusyBox、iptables/ipset、uClibc、管理面、内核/模块 | 多消费者、厂商集成或闭源 ABI 约束 | **不纳入单包升级** | 需要固件级重建、来源条件不具备或回滚风险过高 |

计划中的上游版本仅用于方案估算；真正锁定源码前必须重新核对上游发布、支持周期、源码签名和编译要求。访问日期为 2026-11-09。

## 2. 可行性与利弊

### 2.0 Samba 4.25.1 / 1.0.7-r2d 当前维护与后续升级

设备当前运行 Samba **4.25.1**；`1.0.7-r2d` 是兼容层/安装包版本，新增访客网 SMB 规则和自愈逻辑，Samba payload 与前一包相同。详见 [SMB 1.0.7-r2d 审计](../audits/smb-1.0.7-audit-2026-11-09.md)。上游在计划日期列出的当前 stable 也是 4.25.1，因此**当前没有需要立即部署的 Samba 上游版本升级**。[Samba 发布记录](https://www.samba.org/samba/history/)

本计划把 SMB 任务分为“当前部署收尾”和“未来上游迁移”两条：

| 工作项 | 当前状态 | 执行内容 | 完成门槛 |
|---|---|---|---|
| 1.0.7 当前部署收尾 | 已安装；139/445、ACL、LAN 正向访问、cron 自愈有现场证据；`homes` 共享在枚举中出现 | 只读确认生产 smbd/nmbd 的 exe/版本；核实 `[homes]` 是否预期、实际能否连接/访问；在维护窗口做升级后整机重启核对；访客无线驱动阻止了真实客户端测试，先保持 BLOCKED | 冷启动后 139/445 归属、配置/ACL、cron 和 SSH/管理面均正常；homes 的保留/隐藏决定有证据；访客实测有可用访客 BSS 和客户端后单独补做 |
| Samba 上游版本迁移 | 当前 4.25.1；暂无新版本迁移任务 | 有更新 stable 或安全修复时，重锁源码/依赖/签名，迁移 SDK 适配补丁，比较配置默认值、VFS 和旧内核 syscall，再走完整回归 | 干净重建可复现；隔离、客户端、文件策略、热插拔、设备性能和回滚通过后才部署 |
| 兼容层版本维护 | 1.0.7-r2d | 只有 adapter、ACL、安装器等内容变化时递增包版本；Samba 源码版本与包版本分开标识；每次装机记录输入 tar SHA-256、安装文件清单和运行态证据 | 版本目录、包清单、MANIFEST、rollback 目标和设备日志完全对应；同版本号不重打不同字节 |

**利弊判断：**保持当前 4.25.1 可避免一次没有上游差异的生产切换；代价是上游安全维护需要有人跟踪，不能把“已升级”当作以后无需复查。当前最直接的工作是验证已装 1.0.7 的冷启动与准确进程身份，而不是盲目再构建同一版 Samba。

### 2.1 Dropbear 2011.54 → 当前上游候选

上游发布页当前列出 Dropbear 2026.94；设备上的 Dropbear 2011.54 实际监听 TCP 22，且基线报告记录访客网也能访问。2026-11-09 的防火墙修订证据显示新增访客网拒绝规则只覆盖 SMB 139/445，原厂规则仍对所有接口放行 TCP 22/80，因此 SSH 的访客网可达性尚未因该修订改变。[Dropbear 发布记录](https://github.com/mkj/dropbear/releases) · [1.0.7 防火墙快照](../evidence/2026-11-09-diskacl/install-1.0.7-post-snapshot.txt)

**收益**

- 直接更新当前对外提供 SSH 服务的旧组件；不必替换系统 OpenSSL（Dropbear 在本设备不链接 OpenSSL）。
- Dropbear 可单独放在硬盘私有目录，和 BusyBox、uClibc、系统 OpenSSL 隔离。
- SSH 仍是设备维护和恢复入口，修复新版本后可减少老算法兼容负担。

**代价与风险**

- SSH 接管失误会把维护者锁在设备外；无串口/本地控制台证据，必须把远程恢复列为发布阻断项。
- 编译成功不代表可用：需确认新版在 GCC 4.8.2/uClibc 0.9.33.2 与 Linux 2.6.36 下的 ELF、线程/熵源、密码算法、主机密钥和认证行为。
- 改变算法默认值会让现有客户端或自动化脚本失联；不能通过重新开启弱算法来掩盖兼容问题。
- 单纯升级不修复访客网可达性；限制 22 端口是另一个防火墙配置变更，需单独回归小米管理和远程维护链路。
- 私有程序依赖 `/userdisk/data`；设备盘未挂载时，新服务无法启动。保留原厂 rootfs Dropbear，并让启动入口在私有树缺失时回退到原厂程序。

**建议验证与回滚**

1. 先只在构建机产出，检查 ELF 架构、解释器、动态依赖、`readelf` 符号和可复现输入。
2. 先用备用端口并行启动候选进程，保留原厂 22 端口；验证 LAN 登录、密钥认证、会话稳定、断线重连、SFTP/SCP（如启用）和日志。
3. 接管前确认原厂二进制、配置、主机密钥、启动项哈希备份可恢复；准备自动超时回滚和仍可用的第二会话。若无法提供不依赖新 SSH 的恢复路径，不切换生产 22。
4. 最终检查冷启动、重启后端口归属、远程 App/云端干预、旧入口不会重复拉起原厂进程；只在通过后标记 device-test。

### 2.2 `nmbd` 4.0.21 → 私有 Samba 4.25.1 `nmbd`

设备初始清点记录原厂 `nmbd` 4.0.21 仍占 UDP 137/138；Samba 4.25.1 `nmbd` 已构建且哈希与设备私有树一致。但后续 S8 兼容包装器仍通过原厂 `/usr/sbin/nmbd` 启动它。因此，不能仅凭初始清单认定现在仍在跑旧版；切换前必须重新读取进程 `cmdline`、`/proc/PID/exe`、加载库和版本。

**收益**

- 若当前仍为 4.0.21，可移除最后一个旧 Samba 家族网络监听进程。
- 复用已有 4.25.1 构建和私有 GnuTLS/依赖树，边际构建成本低。
- 139/445 主服务已由同一版 Samba 提供，版本组合更一致。

**代价与风险**

- nmbd 提供 NetBIOS 名称服务与浏览发现；这可能影响电视、旧 Windows/SMB 客户端、网络邻居显示或小米 App 发现。当前证据证明 UDP 监听存在，尚不足以证明哪些客户端依赖它。
- 启动脚本直接调用原厂路径；接线改动可能被固件 init、TaskMonitor 或 App 路径覆盖。nmbd 未登记在 TaskMonitor 表内，不能按 smbd 的接管模型想当然。
- 新版 nmbd 的私有依赖环境、接口绑定、NetBIOS 名称和广播行为需独立验证；新版 smbd 已可用不等于 nmbd 发现行为等价。

**建议验证与回滚**

1. 只读确认当前 nmbd 的二进制身份与 UDP 端口归属；若已是 4.25.1，不重复升级。
2. 在同 LAN 隔离测试设备上核对名称注册、浏览列表、设备休眠/重启后的重新注册、137/138 广播，以及旧客户端发现；不能在生产设备上让两个 nmbd 抢占端口。
3. 将启动路径改成显式的版本化私有二进制和私有 `LD_LIBRARY_PATH`，保存原厂 init 与二进制哈希；生产切换时先停旧实例、确认 UDP 端口释放，再启动新实例。
4. 用可逆单步回滚恢复原厂 `/usr/sbin/nmbd` 启动；分别检查 SMB 139/445 和 NetBIOS 137/138，确认 TaskMonitor/SMB 包装器无副作用。

### 2.3 curl 7.33.0 → 独立 curl 8.x

设备 curl 7.33.0 链接 PolarSSL 1.3.16 与 zlib 1.2.7。上游版本表目前列出 curl 8.23.0；其变更记录注明 8.23.0 删除了 SMB 协议支持，8.18.0 起对 GnuTLS/OpenSSL 的最低版本也已提高。因此，不应照抄“curl 8.x + 现有系统 TLS”作为构建方案。[版本表](https://curl.se/docs/versions.html) · [变更记录](https://curl.se/changes.html)

**收益**

- 新版客户端可更新 HTTP/TLS 协议处理与错误修复，且无需替换系统服务。
- 私有名字（如 `curl-new`）和私有 CA/TLS 库可避免影响系统工具；应用按绝对路径选择新客户端。

**代价与风险**

- 当前没有仓库证据证明设备业务脚本依赖 curl，也未盘点其调用参数、协议、CA 路径和退出码；若无调用方，升级只是增加维护负担。
- 当前 PolarSSL 版本太旧，不能假设与新 curl 兼容。需要选择并单独维护私有 mbedTLS 或其他受支持 TLS 后端，连同证书包、时钟与主机名验证。
- 8.23.0 不支持 SMB URL；检查既有脚本是否使用 `smb://`。同时要验证旧脚本依赖的选项、重定向、代理、HTTP/2、IPv6 与 CA 行为。
- 硬盘掉线或挂载顺序异常时，新 curl 路径不可用；系统原 curl 应保留作诊断/回滚，但不可静默覆盖 `/usr/bin/curl`。

**建议验证与回滚**

1. 只读搜集系统脚本、init、App 调用方对 `curl` 的所有引用及 `curl --version` 能力集。
2. 先构建独立客户端，测试受信任/不受信任证书、主机名错误、系统时间异常、重定向、断点/超时、代理和 IPv4/IPv6；确认依赖完全位于包目录。
3. 将调用方逐个切到显式路径；每个调用保留旧路径回退并比对退出码、标准输出、文件散列和网络副作用。
4. 未发现真实调用方时，将该项停留在候选构建，不安装到路由器。

### 2.4 MiniDLNA 1.1.0 → ReadyMedia 1.3.3（条件候选）

设备初始只读快照中 MiniDLNA 未运行，但 `/etc/config/minidlna` 状态启用；后续发布复核实测原厂 `shareUpdate` 可生成含多个媒体目录的配置并由 `supervisord` 拉起服务。故“不在运行”不等于“功能不用”。可见上游最新发布为 1.3.3（2023 年），版本落后明显，但项目维护活跃度有限。[ReadyMedia 发布页](https://sourceforge.net/projects/minidlna/files/minidlna/)

**收益**：更新 UPnP/DLNA 解析与服务端代码；可保持独立进程，不必动系统库。

**代价与风险**：启动链不仅是二进制，还包括 `shareUpdate` 生成配置、App 启用门控、`supervisord` 看护、媒体目录/权限、索引数据库和电视通知。配置路径或数据库格式变化可能让 App/电视看不到内容。上游版本停留在 2023 年，需先确认其安全/维护收益是否值得迁移。

**建议**：先从用户目标确认 DLNA 是否仍需使用。需要时先在独立目录验证启动、五类媒体路径、目录扫描、增量更新、电视/播放器发现、App 启停与重启持久性；配置仍由原厂链生成，直到逐项证明可替代。未使用则不部署。

### 2.5 dnsmasq 2.71（暂停）

设备清点记录 dnsmasq 未运行、无 53 端口监听，DNS/DHCP 由上游网络提供。上游 2.92 可得，但升级一个未运行的服务不会产生现有收益。

如果未来要让本机承担 DNS/DHCP，需另开网络变更方案：确认谁是现有租约与解析权威、UCI/lease 文件语义、静态租约、DHCP option、IPv6 RA/DHCPv6、防火墙、上游失联回退和重复地址。此项目不得与 SSH 或 curl 升级同一变更窗口执行。

### 2.6 OpenSSL 系统库与 8443 管理端

OpenSSL 1.0.1j 被正在运行的 `sysapihttpd` 加载；设备没有独立 `openssl` CLI。**给新工具带一套私有 OpenSSL 只保护新工具，不会改变 8443 服务实际加载的旧库。** 直接替换 `libssl.so.1.0.0` / `libcrypto.so.1.0.0` 会影响多个厂商程序并可能使管理面无法启动。

因此本计划不把 OpenSSL 作为独立系统包发布，也不将私有 OpenSSL 宣称为 8443 的修复。8443 应先另行只读确认监听、证书/协议配置和管理调用链，再评估厂商支持的 TLS 配置收紧或网络隔离；未证明不影响 App 前不改 `sysapihttpd`。

### 2.7 WebDAV 作为 SMB 的可选补充共享

**可行性结论：有条件可行，值得做隔离原型；不建议直接改小米原有 Web 管理服务，也不应把 WebDAV 当作 SMB 的无缝替代。** 仓库尚无 WebDAV 服务或设备运行证据。最合适的候选是单独编译并运行的 lighttpd `mod_webdav`，监听暂定专用 LAN 端口（例如 TCP 8088，须先做端口冲突盘点），文件根只指向明确批准的硬盘目录。lighttpd 官方说明 `mod_webdav` 支持 PROPFIND、PUT、MOVE、LOCK 等常见方法；完整属性和锁功能需要 libxml2/SQLite，且锁数据库必须放在持久可写目录。[lighttpd `mod_webdav` 文档](https://redmine.lighttpd.net/projects/lighttpd/wiki/Mod_webdav)

**“小米 WiFi 全盘访问”联动：可以实现，但原厂开关不是通用文件服务 ACL。** App 改动 `/etc/config/macfilter` 中设备条目的 `option lan=yes/no` 已有实测；原厂 Samba 反汇编显示此类 MAC 判定主要用于区分 browseable 普通共享与 non-browseable 整盘共享。当前 1.0.7 兼容层进一步把 `lan=no` 解释为拒绝该设备访问 SMB 的 TCP 139/445（UDP 137/138 也进入该链），这是本兼容层的 SMB 行为，不能倒推为原厂跨协议语义。WebDAV 不能仅因共享相同磁盘路径就自动受开关控制。建议明确产品语义为：WebDAV 根目录代表整盘入口，设备在 App 中关闭“全盘访问”时拒绝该设备连接 WebDAV 专用 TCP 端口；打开时仍须通过 WebDAV 自身认证，不能将 `lan=yes` 当成免密登录。访客网默认拒绝，服务只绑定 LAN。要实现该策略，必须把同一只读策略解析器扩展到专用 WebDAV 端口；`mode.lan` 缺失、变成 `whitelist`、配置解析失败或同步故障时，WebDAV 必须关闭或拒绝访问（fail-closed），不能沿用 SMB 当前“拒绝策略后保留现状”的防火墙语义，以免新服务意外敞开。规则需要排在小米宽泛 ACCEPT 前，并验证开关两方向、撤销时延和规则自愈。

**收益**

- macOS、Windows、手机和第三方文件应用可通过 HTTP/WebDAV 客户端访问；无需依赖 SMB 客户端与 NetBIOS 浏览发现。
- 独立端口和独立进程可同现有 SMB 共存，原厂 80/8443 管理链不需要改动。
- 设备访问开关可复用 `macfilter` 中的用户意图，并用 MAC 防火墙规则快速拒绝 `lan=no` 设备；不需要 WebDAV 服务理解小米 UCI。

**代价与风险**

- WebDAV 暴露上传、删除、移动、建目录等远程文件操作；必须有认证和安全的传输方式。未加密 HTTP 下的 Basic 凭据不适合在不可信链路传输；HTTPS 证书信任和旧设备兼容需实测。绝不能把端口转发到公网。
- 小米开关的现有策略是 SMB 专用实现。新服务必须增加 TCP 端口规则、访客网拒绝、配置变更同步、自愈和撤销测试；只复用一段 UCI 解析而漏接规则，可能让 `lan=no` 设备绕过 SMB ACL。
- R2D 使用 Linux 2.6.36、uClibc 0.9.33.2。Go 1.24+ 官方最低内核为 3.2；Go 的 ARM 架构支持表对 Go 1.23 也要求至少 3.1，因此当前 rclone WebDAV 不应作为本机首选。[Go Linux/ARM 最低要求](https://go.dev/wiki/Linux)。现有 nginx 1.2.2 的 DAV 模块既未证明已编译启用，也只实现部分 DAV 方法；官方明确指出依赖额外 WebDAV 方法的客户端不能工作。[nginx DAV 模块文档](https://nginx.org/en/docs/http/ngx_http_dav_module.html)
- lighttpd 方案仍需验证 GCC/uClibc/旧内核编译兼容、模块依赖、SQLite 锁库一致性、中文与大小写文件名、断点/大文件上传、USB/硬盘挂载时序、CPU/内存，以及与 Samba 同时读写的权限语义。作为 C 程序它比当前 Go/rclone 候选更贴合此 SDK，但这只是构建可行性推断，尚无设备验证。
- WebDAV 的账号密码与 `macfilter` 的设备授权是两层控制：共享口令负责身份认证，`lan=no` 负责按客户端 MAC 禁止访问。MAC 可伪造，因此该开关不是强身份认证。若设备更换随机 MAC，需在小米 App 对新 MAC 授权。

**建议验证与部署顺序**

**阶段 0–1 执行进展（2026-11-09）：** SSH 专用 RSA 密钥已成功登录 `192.168.3.2`，本机 Host 配置已支持直接连接。14:29 只读快照确认：1.0.7-r2d 私有 Samba 4.25.1 持有 139/445；nmbd 是原厂 multicall 4.0.21，持有 UDP 137/138；Dropbear 为 2011.54；curl 为 7.33.0。当前 `[homes]` 启用、配置可写，但私有 smbpasswd 为零字节且未列出 Samba 用户，实际内容访问尚未测试。源码归档与签名校验已准备；阶段 1 的完整构建配方和逐包恢复入口仍需补齐，暂不据此进入阶段 2。详见[执行记录](stage-0-1-preparation-2026-11-09.md)。

1. 先只读核对现有 macfilter 的实际模式、设备条目、WebDAV 端口占用、磁盘路径/属主/权限，以及 guest/LAN/WAN 接口和现有入口顺序；保持管理 80/8443 和 SMB 139/445 不变。
2. 用独立目录和测试数据构建 lighttpd `mod_webdav` 候选，不接入生产 init/App。先以只读方法验证客户端挂载、列目录和下载；再单独验证认证、HTTPS、PUT/MOVE/DELETE 与断点续传。首轮不暴露全盘，优先测试一个明确的共享根目录。
3. 独立实现/扩展 ACL 同步：以 `macfilter` 为单一事实源，专用 WebDAV TCP 端口上将 `lan=no` 拒绝，guest 与 WAN 拒绝；对黑名单模式异常、配置不可读、服务未获准启动时 fail-closed。按下述时限测试 `yes→no` 撤权、`no→yes` 恢复、已有连接终止、规则重建、重启和回滚。
4. 核对服务运行用户对目标文件的权限，避免以 root 提供可写全盘；若必须覆盖混合属主目录，先设计专用组/最小权限映射，并检查对 Samba/小米 App 文件行为的影响。
5. 只有客户端矩阵、认证/TLS、跨服务并发、guest/LAN ACL、资源占用、整机启动和回滚均通过后，才在独立维护窗口部署；WebDAV 仍为 SMB 可选补充，不更改 SMB 的共享语义。

### 2.8 WebDAV 授权验收标准（待实现）

以下数值是设计目标，须由设备测试证明后才允许正式启用：

- 从 `macfilter` 成功落盘起，关闭授权后最多 5 秒拒绝该设备的新连接与新请求；打开授权后最多 5 秒恢复连接资格，仍须认证。
- 撤权须在同一 5 秒上限内终止已有 HTTP keep-alive、下载与上传；不能只依赖新连接规则。中断上传不得发布为完整文件，临时文件清理和跨服务可见性须验证。
- 同步器至少每秒更新一次健康租约；独立看护在租约超过 5 秒、策略不可读/解析失败或规则无法确认时，最多再过 1 秒停止 WebDAV 并拒绝入口。看护本身失效的处理也必须验证；不得用无人检查的状态文件宣称 fail-closed。
- 服务启动顺序为：挂载与目录身份核对 → 默认拒绝入口 → 策略/认证/TLS/权限检查 → 健康看护就位 → 监听。IPv4、IPv6、guest、WAN 与规则被删除/重排均纳入测试；未实现某地址族时不得监听该地址族。
- 测试记录必须包含策略落盘、规则生效、连接终止时间及客户端结果；上述时限无法达到时先修订设计并重新审计，不能静默降低验收要求。

### 阶段 3：隔离功能回归

- **Samba**：复跑 SMB1/2/3 与 macOS/Linux 客户端矩阵、guest/认证、MAC 策略、摄像机只读时段、U 盘挂载共享、并发/签名/加密、旧内核回退和资源指标；复核正常停止/崩溃/重启及版本回滚。
- **`[homes]`**：对有意测试的 guest 与有效用户分别验证枚举、tree connect、目录内容和写入权限；确认是否为产品需要。若不需要，先评估将 `homes=0`、渲染时省略 `[homes]` 的影响，再用独立版本和回滚验证移除；不得把 `browseable=no` 当成访问控制。
- **WebDAV（可选新功能）**：隔离验证 lighttpd WebDAV 客户端兼容、认证/TLS、只读与写操作、大文件/断点、文件名和资源占用；然后单独验证它对同一 `macfilter` 的 `lan=no` 撤权、guest/WAN 默认拒绝、重启自愈与 fail-closed。允许在受控维护窗口启动临时验证实例：独立端口、专用测试目录、测试账号，默认拒绝入口，仅放行指定 LAN 测试客户端；不接入生产 App/init、不设为开机默认。先验证默认拒绝和停止入口，再执行客户端、授权与故障测试。全部通过后才允许正式启用。
- 访客网络 ACL：规则语义与排序有证据；真实访客端到端测试需有可用访客 BSS 和客户端，当前 BLOCKED。不得把 IPv4 规则面检查表述成 IPv6 测试。
- **Dropbear**：并行端口、认证、密钥、连接保持、断线重连和兼容客户端。
- **nmbd**：隔离 LAN 上的名称注册、广播、客户端浏览/发现与启动重试。
- **curl**：TLS/CA/主机名/时钟/重定向/选项行为与真实调用方输出。
- **MiniDLNA**：仅在用户确认使用后做完整 App/配置/媒体/发现链路验证。
- **dnsmasq**：不在本阶段，除非单独立项并提供网络拓扑与备用 DHCP/DNS。

- 先收尾当前 SMB 1.0.7：整机重启后核对运行树、139/445 归属、设备名单 ACL、访客规则位置、cron 与 SSH/管理面；不要重复安装未变化的 Samba 4.25.1 payload。
- 在 SMB 收尾中单独处理 `homes` 决策：当前只确认它来自 `homes=1` 并在列表中出现；内容访问尚未验证。若用户决定隐藏，再单独做配置/包版本变更与客户端回归，不与其他组件升级同窗。
- WebDAV 只作为新服务候选；若进入设备部署阶段，必须在单独端口通过 `macfilter` 同步扩展“小米 WiFi 全盘访问”限制，并验证 guest/WAN 默认拒绝和 fail-closed；不碰小米管理 Web 服务。
- 未来若 Samba 有新上游版本，单独升级 Samba，先从候选树 A/B，再按 S1–S8 需要的回归与原子回滚部署；不与 Dropbear、iptables 或 DNS/DHCP 变更同窗。
- 其余顺序为 curl 只由显式路径调用；nmbd 确认仍旧后做单实例切换；Dropbear 先并行试运行；MiniDLNA 沿用原厂配置生成/管理链。
- 启动验证分两步：先通过手工临时实例与停止/回滚验证；再在维护窗口安装一次性受保护启动入口，设置独立超时回退与成功标记，验证冷启动、重启和硬盘挂载延迟。失败或未写入成功标记时恢复原厂入口。通过后才持久启用。Dropbear 若没有不依赖候选的可用恢复通道，不进入该启动窗口。

### 阶段 5：收尾与发布准入

- Samba 上游版本、兼容层包版本分别记录；对 1.0.7 类包也记录实际安装 tar SHA-256、MANIFEST、当前树和回滚目标。
- 产物干净复建一致，源代码、补丁、依赖、许可证与散列可追溯。
- 非目标组件的端口归属、共享配置、App 生命周期、无线联网和管理 API 必须保持基线行为。目标组件允许计划中明确列出的变更（例如经单独决定禁用 homes、迁移 nmbd）；每项记录预期差异、验收证据和恢复命令，禁止夹带修改。原厂回滚路径必须始终保留。
- 失败时原子切回上一版本或厂商程序，确认端口、进程、配置哈希、管理 SSH 和联网功能恢复。
- 没有真实 App/客户端条件的功能标为 BLOCKED；“构建成功”不能标为“升级完成”。

## 5. 变更窗口与回滚顺序

1. 先完成不触碰网络服务的 curl 私有候选构建与隔离测试。
2. 若确认仍有旧版 nmbd，再单独切换 nmbd；保留旧入口和当前 Samba 4.25.1 运行树。
3. Dropbear 最后切换，前提是已有备用会话、自动回滚和可用的原厂登录通道；否则仅完成候选测试，不生产接管。
4. MiniDLNA 只在用户确认启用需求后单独安排；dnsmasq、iptables、内核与系统 OpenSSL 本轮不改。

任一阶段出现 SSH 无法新建会话、139/445 变化、DNS/DHCP/无线异常、`sysapihttpd`/App 失效、磁盘挂载变化或无法验证回滚，立即停止后续升级并恢复该组件原版本。
