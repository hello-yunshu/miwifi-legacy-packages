# WebDAV 立项材料（未立项）

- 记录日期：2026-11-09

- 边界：本文件不代表已批准的开发或部署计划；设备上没有 WebDAV 服务，也没有任何实现代码

## 1. 为什么单独立项

WebDAV 是新功能，不是既有组件的版本升级：需要新监听端口、独立的认证/TLS、把小米“全盘访问”开关扩展到另一套规则，并新增一条与 SMB 并行的访问面。它与 SMB 收尾、Dropbear 接管、nmbd 切换的风险结构不同，混在同一计划里会模糊窗口与回滚边界。

## 2. 可行性结论（原文保留）

有条件可行，值得做隔离原型；不建议直接改小米原有 Web 管理服务，也不应把 WebDAV 当作 SMB 的无缝替代。最合适的候选是单独编译并运行的 lighttpd `mod_webdav`，监听暂定专用 LAN 端口（例如 TCP 8088，须先做端口冲突盘点），文件根只指向明确批准的硬盘目录。lighttpd 官方说明 `mod_webdav` 支持 PROPFIND、PUT、MOVE、LOCK 等常见方法；完整属性和锁功能需要 libxml2/SQLite，且锁数据库必须放在持久可写目录。[lighttpd `mod_webdav` 文档](https://redmine.lighttpd.net/projects/lighttpd/wiki/Mod_webdav)

### 2.1 与“小米 WiFi 全盘访问”的联动

可以实现，但原厂开关不是通用文件服务 ACL。App 改动 `/etc/config/macfilter` 中设备条目的 `option lan=yes/no` 已有实测；原厂 Samba 反汇编显示此类 MAC 判定主要用于区分 browseable 普通共享与 non-browseable 整盘共享。当前 1.0.7 兼容层进一步把 `lan=no` 解释为拒绝该设备访问 SMB 的 TCP 139/445（UDP 137/138 也进入该链），这是本兼容层的 SMB 行为，不能倒推为原厂跨协议语义。WebDAV 不会因为共享同一磁盘路径就自动受开关控制。

建议产品语义：WebDAV 根目录代表整盘入口；设备在 App 中关闭“全盘访问”时拒绝该设备连接 WebDAV 专用 TCP 端口；打开时仍须通过 WebDAV 自身认证，不能把 `lan=yes` 当成免密登录；访客网默认拒绝，服务只绑定 LAN。要实现该策略，必须把同一只读策略解析器扩展到专用 WebDAV 端口；`mode.lan` 缺失、变成 `whitelist`、配置解析失败或同步故障时，WebDAV 必须关闭或拒绝访问（fail-closed），不能沿用 SMB 当前“拒绝策略后保留现状”的防火墙语义。

## 3. 收益与风险（原文保留）

**收益**

- macOS、Windows、手机和第三方文件应用可通过 HTTP/WebDAV 客户端访问，不依赖 SMB 客户端与 NetBIOS 浏览发现。
- 独立端口与独立进程可与现有 SMB 共存，原厂 80/8443 管理链不需要改动。
- 设备访问开关可复用 `macfilter` 中的用户意图，用 MAC 防火墙规则快速拒绝 `lan=no` 设备。

**风险**

- WebDAV 暴露上传、删除、移动、建目录；必须有认证与安全传输。未加密 HTTP 下的 Basic 凭据不适合不可信链路；绝不能把端口转发到公网。
- 小米开关的现有策略是 SMB 专用实现；只复用一段 UCI 解析而漏接规则，可能让 `lan=no` 设备绕过 SMB ACL。
- R2D 使用 Linux 2.6.36 / uClibc 0.9.33.2；Go 1.24+ 官方最低内核 3.2，Go 1.23 的 ARM 支持也要求至少 3.1，因此 rclone WebDAV 不应作为本机首选。[Go Linux/ARM 最低要求](https://go.dev/wiki/Linux)。现有 nginx 1.2.2 的 DAV 模块既未证明已启用，也只实现部分 DAV 方法。[nginx DAV 模块文档](https://nginx.org/en/docs/http/ngx_http_dav_module.html)
- lighttpd 方案仍需验证 GCC/uClibc/旧内核编译兼容、模块依赖、SQLite 锁库一致性、中文与大小写文件名、断点/大文件上传、USB/硬盘挂载时序、CPU/内存，以及与 Samba 同时读写的权限语义。
- WebDAV 口令与 `macfilter` 设备授权是两层控制；MAC 可伪造，因此该开关不是强身份认证。设备更换随机 MAC 后需在 App 重新授权。

## 4. 若立项，所需的验收目标（原文草案）

以下数值是设计目标，须由设备测试证明后才允许启用：

- 从 `macfilter` 成功落盘起，关闭授权后最多 5 秒拒绝该设备的新连接与新请求；打开授权后最多 5 秒恢复连接资格，仍须认证。
- 撤权须在同一 5 秒上限内终止已有 HTTP keep-alive、下载与上传；不能只依赖新连接规则。中断上传不得发布为完整文件。
- 同步器至少每秒更新一次健康租约；独立看护在租约超过 5 秒、策略不可读/解析失败或规则无法确认时，最多再过 1 秒停止 WebDAV 并拒绝入口。
- 服务启动顺序：挂载与目录身份核对 → 默认拒绝入口 → 策略/认证/TLS/权限检查 → 健康看护就位 → 监听。未实现某地址族时不得监听该地址族。
- 测试记录必须包含策略落盘、规则生效、连接终止时间及客户端结果；时限无法达到时先修订设计再重新审计。

**与 SMB 的语义冲突**：SMB 侧撤销实测为约 10 秒（重启）与约 22 秒（cron，上限 60 秒），而本节草案要求 5 秒。立项前必须先决定是统一时延语义，还是明确写清两套服务时延不同并让 App 文案可解释。

## 5. 立项前置条件（未满足则保持未立项）

1. 用户明确批准立项，并指定目标客户端、共享目录与读写需求；
2. 端口冲突盘点完成（8088 及候选端口）；
3. 明确“统一撤销时延”还是“两套语义并存”的产品决定；
4. 磁盘路径、属主与最小权限映射方案确定；
5. 回归矩阵与 SMB 的并发读写、掉盘、重启场景一并定义。
