基线：当时的 S0–S8 开发计划（已于 2026-11-09 被《R2D 软件升级总计划与可行性审计》取代并移除）、[决策记录](decisions.md)。审计对象是仓库文档、`recipes/samba` 代码与现场设备（R2D，ROM 2.25.209，`192.168.3.2`）。审计结束时设备停在“新版 `samba-s5d` 在跑”状态，未回退原厂。

审计原则：阶段“完成”必须有可复现证据；只有文档声明、没有现场或隔离测量的，按“未达成/证据不足”处理。S6、S7、S8 的关键数字按要求重新现场取证，不复用旧记录作为唯一依据。

### 4.2 S7 切换窗口（重新测量）

方法：受控 A/B：停新版 → `/etc/init.d/samba.vendor start` → `PROCLINE="/usr/sbin/smbd -D" /usr/sbin/supervisord stop` → `/etc/init.d/samba start`，最终恢复新版。不修改原厂二进制与配置。

| 观测 | 本次实测 |
| --- | --- |
| 停新版 → 139/445 释放 | 同一秒 |
| vendor 启动 → 139/445 监听 | 同一秒 |
| vendor 停止 → 新版监听 | **约 5 秒**（含进程启动与端口就绪） |
| 收尾 | 新版恢复监听，PID 28271（后续 21200/21886，当前 23809） |
| 四个原厂哈希 | 与切换前一致 |

审计结论：**“11 秒切换窗口”表述不准确**。S7 文档里的 11 秒是“原厂 TERM 15:08:36 → 新版停止 15:08:47”，这段时间包含新版运行和 macOS 验证，**不是端口空窗**；真实切换/停机是秒级，本次 vendor→new 约 5 秒。11 秒应改称“接管窗口”，不能当作停机时长对外表述。真正需要关注的是“小于 TaskMonitor 约 14 秒的抢回窗口”，两种测法都满足。

## 5. 表述核验：哪些说过了头

### 5.1 `ROOT_TREE_IDENTICAL`

- 全仓库 grep：**0 命中**。没有找到这条结论或其等价物。
- 事实也不支持“根树相同”：新版树有 `samba-s5d`、S3/S4 补丁、独立库与配置，本来就不应与原厂树相同。
- 正确的回归判据是：四个原厂文件 md5 不变、139/445 归属明确、客户端行为可复现。审计按这三条核对，均成立。
- 结论：**该表述即使在其他场合出现过，也没有仓库证据支撑；不应使用。**

### 5.2 适配器退出码语义

- 文档声明：0 ok、1 runtime failure、2 bad invocation/missing tree、3 config rejected、4 stale/wrong PID、5 port in use、6 reload channel failed、7 config drift。
- 审读发现真实缺陷：`cmd_stop` 在“无 pidfile”和“stale 死 PID”两个分支直接返回 0，即使端口仍被占用；TaskMonitor 的异步 kill 还没完成时也会“假成功”。
- 已修复：三个分支都要求端口真正释放，否则返回 **5**；`status` 的 1（degraded）和 5（端口被他人占用）也补进用法说明。
- 证据：单元测试（端口忙 → rc=5、端口空闲 → rc=0）；生产 `stop`/`start` 实测 rc=0、端口释放/恢复，最终 PID 23809。生产 `stop` 实际走到了“无 live pidfile”分支，说明该缺陷有现实触发场景，不是理论问题。
- 结论：**修复后语义成立；“stop 总是返回 0”不再成立。**

### 5.3 “fail-safe 回退原厂”

- 事实：wrapper 在 `current/hook.sh` 不可执行（回滚，或 `/userdisk/data` 未挂载）时 `exec /etc/init.d/samba.vendor`，这是**代码路径**。
- 未做物理拔盘/坏盘/挂载失败演练，因此只能写“代码路径存在，场景未实测（BLOCKED）”。
- 另一个被混淆的点：`S5_ACCEPT_CONFIG=1` 在 `hook.sh` 的 `start`/`reload` 中**始终设置**，所以生产启动路径不是“配置漂移就拒绝”，而是“记录后接受”。真正的 fail-closed 只在手动 `generate/check/start`（不带该环境变量）时成立。
- 现场证据：审计收尾执行 `stop`/`start` 后，适配器日志 16:47:14 明确出现 `config drift accepted explicitly`，随后重新生成并启动；`/etc/config/samba` 哈希未变（`244eb53e…`）。这说明生产启动确实会接受漂移，不是只在代码里“可能接受”。
- 结论：**“fail-safe 回退原厂”是设计路径，不是已演练能力；“守卫 fail-closed”只在手动路径成立。**

### 5.4 “App 抢不回端口”

- 已验证：`/etc/init.d/samba` 的 `reload/restart/stop/start` 四条入口都落到新版，未出现原厂 smbd；全盘扫描未发现其它二进制直接调用 `/usr/sbin/smbd`。
- 未验证：真实手机 App / 云端下发未操作，App 是否会在某条路径直接 `supervisord start` 原厂条目未证。
- 结论：应表述为“**入口级验证通过，真实 App BLOCKED**”，不能写成“App 一定抢不回端口”。

### 5.5 `md5sum -c` 三项 OK

- 本次实测：`hook.sh`、`xiaomi-smb-adapter.sh`、`samba.init.wrapper` 三项全部 `OK`，属实。
- 但 MANIFEST **只覆盖这 3 个脚本**，不覆盖 `samba-s5d`、`nmbd`、私有库、适配器之外的运行树。把“三项 OK”当作“整棵新版树校验通过”是扩大解释。
- 结论：**三项 OK 成立，覆盖范围需要注明。**

### 5.6 “原厂 smbd 不存在”

- 应为“**没有原厂 smbd 进程**”。文件 `/usr/sbin/smbd` 是 `samba_multicall` 的符号链接，确实存在。
- 判据必须是 cmdline + `/proc/<pid>/exe`；`pidof smbd` 会漏/误命中，`pidof samba_multicall` 会命中 nmbd。
- 结论：**表述需降级并写清判据。**

## 8. 发布阻断项 vs 不影响使用的未测项

### 8.1 真正阻塞“发布”

1. **干净环境复建未完成**：候选清单要求“干净复建产物与清单散列一致”，本轮未重跑；适配器/兼容层改动后也没有完整重建链。

## 12. 最终判断

项目**没有“做完”**：作为“实机长期运行新版 SMB”的替换工程，它已经基本成功（约 90%）；作为按 S0–S8 定义、可以对外发布的交付物，它完成约 **82%**，发布就绪约 **55–60%**。

设备当前状态符合预期：139/445 由新版 `samba-s5d`（PID 23809）持有，nmbd 23868，7 个共享，四个原厂哈希未变，`install.sh rollback` 可完整回原厂。审计没有把设备改回原厂。

## 附录：复现命令

以下命令均在设备上执行（`ssh -i ~/.ssh/id_rsa_miwifi_r2d -o HostKeyAlgorithms=+ssh-rsa -o PubkeyAcceptedAlgorithms=+ssh-rsa -o KexAlgorithms=+diffie-hellman-group14-sha1 root@192.168.3.2`）。

```sh
# 139/445 归属与 exe 判据
netstat -lntup 2>/dev/null | grep -E ':(139|445) '
for p in $(pidof samba-s5d); do echo "$p $(readlink /proc/$p/exe)"; done
# 原厂 smbd 进程（应为空；/usr/sbin/smbd 文件本身是符号链接）
for d in /proc/[0-9]*; do
  c=$(tr '\0' ' ' <"$d/cmdline" 2>/dev/null); c=${c% }
  [ "$c" = "/usr/sbin/smbd -D" ] && echo "vendor: ${d#/proc/} $(readlink $d/exe)"
done

# 配置/版本/前缀链接
md5sum /etc/config/samba /etc/config/misc /var/etc/smb.conf /usr/sbin/samba_multicall
readlink -f /userdisk/data/s7root/current
readlink -f /userdisk/data/samba-s2/root

# 兼容层校验
cd /userdisk/data/s8compat/versions/v1 && md5sum -c MANIFEST
sh /userdisk/data/s8compat/stage/install.sh verify; echo "verify_rc=$?"

# 适配器状态
/userdisk/data/s8compat/versions/v1/xiaomi-smb-adapter.sh \
  -r /userdisk/data/s7root/current -p "139 445" -P status; echo "status_rc=$?"

# 任务表条数（2812 B/记录）
ls -l /tmp/taskmonitor/taskmonitor.conf
```

S6 吞吐复现方法见 §4.1（隔离树 1445、guest、`server signing = no`、128 MB、设备本地 `smbclient`）；S7 切换复现步骤见 [s7-switch-rollback.md](s7-switch-rollback.md) 的“审计复测”。
